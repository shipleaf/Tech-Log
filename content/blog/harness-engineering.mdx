최근, 여러 매체에서 너도나도 하네스 엔지니어링을 비롯해 AI Agent를 '잘' 활용하기 위한 방법을 공유하는 분위기가 이어지고 있습니다.
이 글을 통해 제가 하네스 엔지니어링을 설계하며 했던 고민들과 문제해결들을 공유하고자 합니다. 하네스 엔지니어링을 설계하거나, 배워보고자 하는 모든 분들께 도움이 되기를 바랍니다.

## 프롬프트 엔지니어링, 컨텍스트 엔지니어링

AI 등장 이후, AI의 코딩 능력이 향상되면서 **어떻게 AI를 활용해서 더 생산적으로 코딩을 할 수 있을까?** 에 대한 연구가 이어지고 있습니다.

### 프롬프트 엔지니어링

프롬프트 엔지니어링(Prompt Engineering)은 AGENT 등장 이전, LLM에게 원하는 대답을 얻기 위해 프롬프트에 입력하는 양식을 의미합니다.
기법과 예시를 살펴보면,

- 역할 부여: LLM에 페르소나를 지정하여 보다 질문에 전문적인 답변을 얻기 위한 기법입니다.
- 출력 양식 지정: 답변을 어떤 형태로 받을지 정하는 기법입니다.
- 제약 조건 부여: 답변의 길이, 문체, 수준, 포함할 내용, 제외할 내용을 정하는 방법입니다.
- 대상 독자 지정: 누가 이해해야 하는 답변인지 정하는 기법입니다.
- 예시 기반 지시: 원하는 답변 방향을 예시로 보여주는 방법입니다.

```
# 역할 부여

너는 5년차 프론트엔드 면접관이야. 신입 면접처럼 질문해줘
React를 처음 배우는 백엔드 개발자에게 설명하듯이 알려줘.

# 제약 조건 부여

800자 이내로 작성해줘.
너무 과장하지 말고 실무 중심으로 작성해줘.
신입 프론트엔드 개발자 수준으로 답변해줘.
코드 예시를 포함해줘.
```

### 컨텍스트 엔지니어링

컨텍스트 엔지니어링(Context Engineering)

## 하네스 엔지니어링의 등장 배경

앞서 소개한 프롬프트 엔지니어링, 컨텍스트 엔지니어링은 컨텍스트가 비대해지거나 컨텍스트와 맞지 않은 명령을 내리거나 모호한 명령을 내렸을 때,
AI가 멋대로 판단하거나 작업을 모두 완료하지 않았지만 종료해버리는 문제가 있습니다. 이는, 개발자에게 반복적인 수정과 추가적인 명령을 하게 되고,
이는 곧 개발의 병목이 됩니다. 이 문제를 해결하기 위해 나온 것이 **하네스 엔지니어링**입니다.

하네스 엔지니어링은 정해진 틀, 규범은 없습니다. AI Agent를 의도대로 동작하도록 제어하고 테스트하는 모든 과정과 방식이 포함됩니다.

에이전트가 md 파일을 통해 읽도록 하는 방법도 있지만, 더 강제성을 부여하기 위해서는

프롬프트 엔지니어링 → 컨텍스트 엔지니어링(일의 히스토리, 단순 md) → 하네스 엔지니어링

우리는 소프트웨어 엔지니어링 팀의 주된 업무가 더 이상 코드 작성에서 벗어나 환경을 설계하고, 의도를 명시하며, Codex 에이전트가 안정적인 작업을 수행할 수 있도록 피드백 루프를 구축하는 것으로 바뀔 때 어떤 변화가 발생하는지 이해

더 이상 개발자는 코드 작성에 그치는 게 아니라, AI를 관리하고 올바르게 개발할 수 있도록 조정하는 역할이 된다.

여기서, 하네스 엔지니어링의 핵심은 AI 에이전트 작업의 병목이 되는 “사람”의 역할을 최소화 하는 것, 그마저도 AI에게 맡기는 것입니다.

모델에게 단순히 “더 잘해봐”, “아니 그게 아니라”라고 말하는 것이 아니라, 모델이 최고의 성능을 발휘할 수 있도록 환경적 설정을 해주어야 한다는 말입니다. 엔지니어링 팀의 주된 역할은 에이전트가 유용한 작업을 할 수 있도록 환경을 만드는 것이 되었습니다.

기존 소프트웨어 엔지니어링하네스 엔지니어링

코드를 직접 작성환경을 설계PR을 한 줄씩 리뷰의도(intent)를 명세개인 코드에 대한 소유감코드는 소모품으로 취급코드 품질에 집중피드백 루프를 구축

## 3. 핵심 구성 요소들

### (1) 컨텍스트 엔지니어링 — "지도를 줘라, 매뉴얼 말고"

가장 초기에 배운 교훈은 단순했습니다: **Codex에게 지도를 줘라, 1,000페이지 매뉴얼이 아니라.** "하나의 거대한 AGENTS.md" 접근법을 시도했지만 예측 가능한 방식으로 실패했습니다. 컨텍스트는 희소한 자원이기 때문에 거대한 지시 파일은 작업, 코드, 관련 문서를 밀어내고, 에이전트는 핵심 제약을 놓치거나 잘못된 것을 최적화하게 됩니다. 모든 것이 "중요"하면 아무것도 중요하지 않습니다. [Jaytaylor](https://jaytaylor.com/notes/node/1770842156000.html)

대신 OpenAI가 채택한 문서 구조:

- **agent.md** — 에이전트가 하면 되는 것과 해야 하는 것에 대한 고수준 컨텍스트
- **spec.md** — 상세 기술 명세
- **core-beliefs.md** — 팀 구성, 제품 비전, 고객 세그먼트, 12개월 로드맵
- **tech-tracker.md** — 비즈니스 로직 검토를 위한 가이드라인
- **quality-score.md** — 에이전트가 요구사항과의 정렬을 평가하고 후속 작업 제안

이 문서들은 동시에 **사람이 읽는 지식 베이스**이자 **에이전트를 위한 프롬프트 컨텍스트** 역할을 합니다.

- 폴더 구조
  ```markdown
  AGENTS.md
  ARCHITECTURE.md
  docs/
  ├── design-docs/
  │ ├── index.md
  │ ├── core-beliefs.md
  │ └── ...

  │ ├── completed/

  ├── generated/

  ├── product-specs/

  ├── DESIGN.md

  ```

### (2) 아키텍처 제약의 기계적 강제

팀은 리포지토리에 "황금 원칙(golden principles)"을 인코딩하고, 백그라운드 Codex 작업이 주기적으로 위반 사항을 스캔해서 타겟 리팩토링 PR을 여는 자동화된 반복 정리 프로세스를 구축했습니다. 대부분 1분 이내에 리뷰하고 자동 머지할 수 있습니다. 기술 부채는 고금리 대출처럼, 소규모로 지속적으로 상환하는 것이 훨씬 낫습니다. [Jaytaylor](https://jaytaylor.com/notes/node/1770842156000.html)

구조화된 리포지토리, 애플리케이션의 에이전트 가독성(legibility) 확보, 아키텍처 제약의 기계적 강제가 핵심이었습니다. [Medium](https://medium.com/@richardhightower/openais-harness-engineering-experiment-zero-manually-written-code-100a24ad04cf)

### (3) 관찰성(Observability)을 1급 인프라로

팀은 첫날부터 포괄적인 관찰성 인프라를 구축했습니다. 로그 집계(Vector), 메트릭 저장소(VictoriaMetrics), 시각화(Grafana), 분산 트레이싱 — 모두 자동으로 부팅되는 형태로. 이 관찰성 인프라는 에이전트에게 문제를 자율적으로 진단·수정할 컨텍스트를 제공합니다. [ZenML](https://www.zenml.io/llmops-database/extreme-harness-engineering-building-production-software-with-zero-human-written-code)

관찰성은 또한 **사전 머지 코드 리뷰에서 사후 머지 리뷰로** 인간의 역할을 근본적으로 바꿉니다. 사람은 배포 후 대표 샘플을 리뷰하면서 실수의 패턴을 찾고, 이 인사이트를 다시 문서, 테스트, 리뷰 에이전트에 인코딩해 지속적인 개선 루프를 만듭니다. [ZenML](https://www.zenml.io/llmops-database/extreme-harness-engineering-building-production-software-with-zero-human-written-code)

### (4) 스킬(Skills) — 엔지니어링 취향을 코드화

팀은 Codex "스킬" — 재사용 가능한 능력 번들로 엔지니어링 취향과 공통 워크플로우를 인코딩한 것 — 을 광범위하게 활용합니다. 놀랍게도 전체 코드베이스가 단 6개의 스킬로 운영됩니다. 네트워크 호출에 타임아웃이 필요하다고 파악되면, 이것이 스킬로 인코딩되어 이후 모든 작업이 자동으로 적용합니다. [ZenML](https://www.zenml.io/llmops-database/extreme-harness-engineering-building-production-software-with-zero-human-written-code)

예를 들어 `$land` 스킬은 PR 전체 생명주기를 코치합니다: PR 푸시 → 리뷰어 대기 → CI 대기 → 플레이크 수정 → 충돌 처리 → 머지 큐 투입 → 완료.

CI/CD(테스트, 병합) 과정이 강제됨

## 7. 당신의 프로젝트에 도입할 때 핵심 원칙

하네스 엔지니어링을 직접 도입할 때 고려할 실천 원칙들을 정리하면:

**① 환경 진단 우선**
에이전트가 실패하면 "더 좋은 프롬프트"를 고민하기 전에, 어떤 도구·추상화·문서가 없어서 실패하는지 파악하고 그것을 만드세요.

**② 컨텍스트는 계층적으로, 진보적 공개(progressive disclosure)**
하나의 거대한 매뉴얼 대신, 디렉토리별 AGENTS.md로 쪼개고 필요한 것만 불러오는 구조로 설계하세요.

**③ 아키텍처 원칙은 문서가 아닌 자동화로 강제**
커스텀 린터, 구조적 테스트로 원칙 위반을 자동 감지하고, 주기적 정리 에이전트로 기술 부채를 지속 관리하세요.

**④ 관찰성을 처음부터**
에이전트가 로그·메트릭·트레이스에 접근할 수 있어야 자율적으로 디버깅하고 수정할 수 있습니다.

**⑤ 코드는 소모품으로 취급**
코드에 감정적 소유감을 갖지 않고, 잘못된 방향이면 과감히 폐기하고 다시 시작하는 문화가 핵심입니다.

⇒ worktree를 폐기하고 과감하게 다시 시작하는 방향, 선 검토 후 병합이 아니라, 선 병합 후 검토

**⑥ 에이전트가 접근할 수 없는 컨텍스트는 존재하지 않는 것**
중요한 컨텍스트를 Google Docs, Slack 스레드, 팀원의 머릿속에 두지 마세요. 에이전트 관점에서 실행 중에 컨텍스트 내에서 접근할 수 없는 것은 사실상 존재하지 않는 것입니다.

## 사용법

1. 반드시 먼저 플랜을 생성 후 작업
2. worktree에서 작업
3. 테스트 코드 작성 필수
4. 검증(빌드, 린트 등)
5. 커밋 → 머지 → 완료의 흐름

프롬프트(컨텍스트)와 함께 코드(bash)로 검증, 하네스를 걸자!

마지막 배쉬에 플랜이 없거나, 테스트를 안했거나 하면 폐기

눈이 바로 로그 시스템이다.

여러 자료를 보면서 느낀 점. 직접 해보고 나에게 맞는 세팅을 하는 수밖에 없다.

해보면서 병목이 발생하는 부분을 진단하고, 최대한 자동화를 하며 업무 속도를 향상시키는 방법을 고민하는 게 맞을듯

## 하네스의 3개 층

**1. Context Engineering (우리가 만든 것)**
— AGENTS.md, docs/, 설계 문서들
— 에이전트에게 "무엇을 해야 하는지" 알려주는 층
— 문제: 에이전트가 이걸 읽고도 틀린 코드를 짤 수 있음. 강제성이 없음.

**2. Mechanical Constraints (아직 없음)**
— 린터, 구조적 테스트, CI 파이프라인
— 에이전트가 레이어를 위반하면 **빌드 자체가 실패**하게 만드는 것
— 문서에 "금지"라고 써도 에이전트는 실수할 수 있지만, CI가 차단하면 물리적으로 불가능해짐
— 이게 없으면 규칙은 권고사항일 뿐

**3. Feedback Loops (아직 없음)**
— Garbage Collection 에이전트, 자동화된 품질 검사
— 문서 stale 감지, 테스트 커버리지 추적, 반복 실수 패턴 분석
— 시스템이 스스로 건강을 유지하게 만드는 층

을 만들어야 함.

AGENTS.md는 **Codex의 행동 가이드**고, CI는 **결과물의 품질 보장**

**AGENTS.md에 PR 생성을 완료 조건으로 명시**
"PR을 열지 않은 태스크는 완료된 것이 아니다" 라고 명확하게 정의해요.

**태스크를 작게 쪼갠다**
태스크가 크면 중간에 뭔가 빠질 확률이 높아요. PR 하나 = 명확한 목적 하나로 범위를 좁히면 Codex가 끝까지 완주할 확률이 높아져요.

하네스 엔지니어링은.. 사실 별 거 없는 것 같습니다. AI가 틀에 벗어나지 않고 개발을 할 수 있게 이끄는 방식이 변해온 방향이 어쩌면 당연하게도 느껴집니다.

하네스 엔지니어링의 속도가 오히려 개발 속도를 늦추는 게 아닌가..라는 생각이 드는데, 하네스 엔지니어링도 세팅하는 사람의 역량에 매우 영향을 받는 것 같습니다(제가 역량이 매우 부족합니다).

## 하네스 리팩터링

1. 너무 모호한 명령을 없앤다.

하네스에게 어느정도의 자율성을 줄 것인가?
